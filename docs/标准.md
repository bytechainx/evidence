# evidence 标准

**crate**：`evidence` v0.1.0 · 依赖：`sha2`、`thiserror`、`async-trait`（运行时零内部耦合）

本文件把 `src/lib.rs`、`src/binding.rs`、`src/lineage.rs`、`src/sign.rs`、`src/query.rs`
的既有语义固化为可断言的条款；章节标题即 SDD 对照表的映射键。

## 1. 定位

- 本 crate 是 L1 审计证据追加面：只负责**校验、规范化、追加回执**与只读查询，
  领域 DTO 与 provenance 的所有权留在领域层。
- 不依赖 `kernel` / `contracts` / `config` 等主工程 crate，不形成反向业务依赖；
  它不复制业务 DTO，也不宣称远程审计服务、签名链或完整合规产品。
- 唯一追加 seam 是 `EvidenceStore`（同步）与并列的 `AsyncEvidenceStore`（远程异步 port）；
  只读面是 `EvidenceReader`。

## 2. 数据模型标准

- `EvidenceRecord` 由六字段构成：`event` / `code_version` / `input_snapshot` /
  `raw_batch_ids` / `result_digest` / `outcome`。
- 构造即校验（`EvidenceRecord::new`）：必填字段非空；`event` / `code_version` /
  `input_snapshot` / `outcome` 不得含行协议保留字符 `|`、`\t`、`\r`、`\n`。
- `raw_batch_ids` 至少一条，且每个元素额外禁止逗号（逗号是列表分隔符）。
- `result_digest` 必须是 **64 位 ASCII 十六进制**；`ReceiptBinding::source_commit`
  必须是 **40 位 ASCII 十六进制**。
- `canonical_line` 固定为
  `evidence-record/v1|{event}|{code_version}|{input_snapshot}|{id1,id2}|{result_digest}|{outcome}`，
  不含追加序号与行结束符；`canonical_bytes` 即该行的 UTF-8 字节。
- `ReceiptBinding::canonical_line` 固定为
  `evidence-binding/v1|{source_commit}|{environment}|{artifact_digest}`。
- `artifact_manifest_digest` 先按路径排序再逐条 `{path}\t{digest}\n` 拼接后取 SHA-256，
  因此与输入顺序无关。

## 3. 追加语义标准

- `append` 返回的 `AppendReceipt.seq` 从 **1** 开始单调递增，`record` 为被追加记录的克隆。
- `append_idempotent` 以规范化记录为幂等键：命中已有记录时原样复用该回执（含原 seq），
  不产生新行；`MemoryEvidenceStore` 与 `FileEvidenceStore` 均实现该能力。
- 未实现幂等追加的适配器，其 `append_idempotent` 默认返回
  `EvidenceError::IdempotencyUnsupported`，避免调用方把普通追加误认为可安全重试。
- `append_with_binding` 写入 `ReceiptBinding`；未实现的适配器默认返回
  `EvidenceError::BindingUnsupported`。幂等键相同但 binding 不一致时返回
  `EvidenceError::BindingMismatch`，不得静默覆盖。
- `durability()` 由实现自己声明：`MemoryEvidenceStore` 为 `Volatile`，
  `FileEvidenceStore` 为 `LocalDurable`；调用方据此决定能否用于生产路径。
- 关闭后必须 fail-closed：`MemoryEvidenceStore::close` 之后的任何追加返回
  `EvidenceError::Closed`。
- 文件行协议为 `{seq}\t{canonical_record}` 或 `{seq}\t{canonical_record}\t{binding}`；
  追加后执行 `flush` + `sync_data`；重开时逐行解析，序号必须严格递增且从 1 起。

## 4. 完整性标准

- `sha256_hex` 输出小写十六进制，长度为 64；对同一 payload 恒定。
- `parse_line` 是 `receipt_line` 的逆运算：解析 `seq`（拒绝 0 与非数字）、record payload
  （要求 7 段且首段等于 `evidence-record/v1`）与可选 binding（要求 4 段且首段等于
  `evidence-binding/v1`），任一段不合法返回 `EvidenceError::InvalidWire`。
- `sign_canonical` 用注入密钥对 `key ‖ role ‖ signer_id ‖ signed_at_ms ‖ payload` 取 SHA-256；
  空 `signer_id` 返回 `EvidenceError::EmptySignerId`。
- `verify_canonical` 重算签名并逐字比较：签名不含 payload、payload 被换、时间戳被改
  任一情况都返回 `EvidenceError::SignatureInvalid`。
- `verify_approval` 实现 `signed → approved` 状态机：Owner 必须先签、Reviewer 后批，
  角色颠倒返回 `EvidenceError::InvalidApprovalRole`，随后两枚签名都须通过 `verify_canonical`。
- `ImmutableBinding` 字段私有，仅 `sign` 可构造；Owner 签名覆盖
  `evidence-immutable-binding/v1|commit|schema|environment|artifact_digest`，
  篡改任一字段或签名使 `verify` / `verify_binding` 失败。
- `LineageBinding` 的 `raw_sha256` 为 64 位十六进制，`pit` 为 RFC3339 时间戳或
  长度 ≥13 的 Unix 毫秒数字串，否则返回 `EvidenceError::LineageInvalid`；
  `DecisionComposition` 至少含一条绑定，`verify_composition` 独立复验全部不变量。

## 5. 验收

```bash
cargo fmt --all -- --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-features
cargo package --no-verify
```

测试至少覆盖：记录与绑定的构造校验（空字段 / 保留字符 / 摘要格式）、
`canonical_line` 形状与 `parse_line` 往返、内存与文件两类实现的序号单调与幂等复用、
文件 opener 的跨进程 / 同进程 / hard-link fail-closed、以及签名与审批角色。
